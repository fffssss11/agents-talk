# Agents Talk 启动编排

交付一组用户可分别粘贴到真实客户端的启动提示词。规划完成即交付，不自动接入、派工、创建客户端任务、启动后台进程或替其他成员发言。用户明确另行要求执行时，再遵循对应执行流程。

## 获取实际约束

从同目录 `location.md` 找到协作项目和 Python 的绝对路径，读取项目 `PROTOCOL.md` 及同级 `agents-talk/SKILL.md`。安装目录缺少后者时读取项目 `skills/agents-talk/SKILL.md`。协议是协作规则的唯一来源；本 skill 只规定如何编排提示词，不复制整份协议给每名成员。

区分协作面板项目与此次业务项目。核对用户提供的业务目录、入口规则和必要的文件结构，只读最少材料，不扫描客户端私密记录，不假定已有测试命令或工具可用。业务目录未提供时不要把本面板目录当成业务目录。

需要现有会话元数据时，保留 location 中的实际 Python、hub.py 及 --data-dir / --config 参数运行 `sessions`，只核对编号、状态、主管、参与名单和上下文模式。规划阶段不调用会刷新读取心跳的 `read / listen`，不直接读取日志或通过人工接口扩大范围。已在真实协作中需要续规划时，可在自己的身份和现有上下文范围内按协议读取；不能假装已获得主管全队视图。

同客户端多窗口按实例拆分：核对每个实例 ID、client、模型标注和角色，一个主导、多名协同/验收。两个 Codex 使用相同模型时仍分别生成提示词，--to / reviewer 指向准确实例 ID，不都写 codex。实例未创建时列为面板启动前设置项，不编造可执行编号，也不声称模型已选择。当前模型由用户在对应客户端核对；同实例不得自审，不同实例可独立验收。

提取用户已给的信息：
- 本次目标、交付物、验收标准及排除范围。
- 指定的主导实例、参与实例及其客户端/模型标注、已知工具与限制。
- 业务工作目录与授权范围。
- 要复用的看板会话，或要新开会话；上下文共享偏好。

只集中询问缺失且会改变分工的问题，通常不超过四项，不重复问已知信息。目标和主管未指定时要询问，不能凭配置替用户指定。新任务不要自动塞进现有 main 会话。新会话可先交付标有 `待设置会话编号` 的草案，告知用户在面板创建并填入同一实际编号后再发送；不要伪造会话已存在。

未指定参与名单时提出 Codex、Claude、Reasonix 参与且 ZCode 不参与的建议，明确这只是待确认方案；用户指定名单优先。只在参与名单内拆分任务，不为凑齐四个客户端强行安排工作。不确定的验收裁量或范围保留为待确认，不擅自增加功能、预算或时间要求。

## 拆分并检查可执行性

按交付物和文件边界拆分，给每项拟定任务编号、负责人、输入依赖、交付位置、验收证据和审查安排。任务编号标明“拟定”，由主管接入后核对是否重名再创建。少量紧密耦合工作可串行，独立模块可并行；依赖不得成环。共同配置、入口或同一文件指定唯一写入负责人，其他成员提供接口建议或审查，避免用笼统的“共同开发”分工。

分工表的依赖落实为 depends_on，写入范围为 files，独立验收人为 reviewer。需要整合时列出整合任务的负责人、前置交付、独立验收人和整合方法，由主管按协议发布 stage=integration 与 integration_plan，计划调整用 workflow 记录。主管按前置到后续的顺序创建，不使用尚未创建的编号。提示词说明前置审查通过再执行，以及认领、重读版本、申请占用、重读文件、修改、交付、释放、审查的顺序。

审查以“目标任务待审查且释放占用”为触发条件，列出明确审查安排即可；不要创建 depends_on 指向被审查任务的审查任务，这会等待它自己的审查结果。聚焦模式的审查材料由主管定向提供，只读指定证据，不能假定审查角色自动获得同伴任务的查询权限。

主管承担任务发布、依赖转达、集成与验收协调，可负责具体模块。执行者只接收自己的目标与必要接口，不给每人粘贴全队计划或业务资料全集。全局上下文开启时也先读成果摘要，详细证据按需查询。其他成员尚未交付时等待主管提供依赖，不能编造接口结果。

编排时核对协议中这些约束，具体操作由执行提示词引用协议：
- 参与名单与主管一致；与现有会话不一致时列为启动前设置项，不自动修改，也不向未启用成员派工。
- 图片制作、图像处理、视频内容制作从混合任务中拆出，标明媒体类型，只分给参与中的 Codex 或 Claude。工具可用性仍需真实验证；没有合适成员时列出阻碍，不改派 Reasonix/ZCode。参考图片等缺失输入明确列出。
- 指定参与中的独立成员为任务 reviewer，未指定时遵循协议的角色回退规则，不能自审。主管自己的交付也需独立验收；仅一名成员时明确缺少条件。聚焦模式由主管定向转交最小证据，不能假设指定验收人能读取全部同伴任务，也不能绕过查询范围。
- 普通工作遵守协议的 workspace 写入边界。外部业务代码库若未建立合法文件占用与协作方式，列为启动阻碍，不凭一段提示词宣布已获得外部目录锁保护。
- 已有任务或材料不可见时如实说明；先让主管接入核对并消除重复，不把拟定分工作成已派发记录。

## 输出给用户

使用 [prompt-format.md](prompt-format.md) 的结构，根据实际任务填写内容，保留足够明确的验收要求。输出：
1. 简短启动摘要：任务、主管、参与名单、业务目录、会话与待确认项，区分已核对和待核对。
2. 每个参与实例一段独立代码块，标题指明客户端、实例 ID 和角色，同客户端多窗口也逐实例输出。主管提示词包含完整分工；执行者提示词仅含自己的任务、依赖和必要约束，不复制其他成员的提示词。
3. 发送顺序：先确认看板设置及工作边界，把主管段发给指定主导；其核对并建立任务后，将对应段分别发给其他参与成员。说明每段只发到对应客户端，提示词生成不等于实际接入。

所有可立即发送的提示词填写实际路径、身份、主管、参与名单和已确认会话编号。尚缺关键字段时明确标成草案并列出替换项，不把留空模板称为可直接执行。生成的是自然语言任务提示词，不硬套所有客户端都支持的斜杠命令。要求各接收者调用原 `agents-talk` skill；Claude 按安装版完成原生窗口绑定，不能用本规划 skill 代替其协作 hook。

交付前检查：每项需求有负责人或明确阻碍；无未参与成员、越界写入、媒体误派、自审、循环依赖；每个代码块可单独理解；主管和执行段的任务编号、交付接口及验收一致；没有声称已执行、已安装工具、已验证通过或能够无限后台运行。用户修改目标、主管或名单后，重新检查受影响的分工并重发对应提示词，保留无关决定。
